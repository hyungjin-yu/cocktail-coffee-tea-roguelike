## 2. 출처 가설(정적 조사, 소스 수정 없음)

| 가설 | 근거 | 평가 |
|---|---|---|
| A. 게임 내부 자동 진행 코드(캡처·시연) | 제출 빌드 `CCT.Contest.dll`에서 `ContestCapture`·`Demo`·`captureFramerate` 문자열 0건(캡처 빌드에서는 각각 7·11·1건). `VirtualHold`에 값을 쓰는 코드는 `ContestCapture.cs`(`#if PPS_CAPTURE`)에만 있다. `ContestApp`의 코루틴은 검수 행 표시(`RevealRows`) 하나뿐이다 | 근거상 배제 |

| C. 키를 누른 상태가 남아 있다가(포커스 획득 시 등) 들어감 | 게임 단축키는 `wasPressedThisFrame`(눌린 순간)만 본다. 남은 키 하나로는 많아야 한 번 반응한다. 그런데 관찰된 변화는 서로 다른 동작 12회 이상이다(시작, 6항목 확인, 진행, 공급안 선택, 주문, 입고 2회). 임무 선택 화면에서는 Enter로 임무를 시작할 수 없어 숫자 `1` 또는 해당 버튼 클릭이 따로 있어야 한다 | 단독 원인으로는 맞지 않음 |

## 3. 그 밖의 요청 항목

- **오디오:** 공모전판은 `AudioService`를 만들지 않는다(`EnsureCreated` 미호출). 버튼 포커스 효과음 훅(`UiFocusSfx` → `AudioService.PlaySfx`)도 인스턴스가 없으면 바로 반환한다. **공모전판은 소리 없는 게임이다(의도된 범위).** 기능을 늘리지 않았다.
- **720p 검수 행 글자 약 10px:** 2026-11-11 오프스크린 렌더와 감사에서 잘림은 0건이었다. 자동 맞춤(최소 14pt × 0.667배)으로 글씨가 작아진 것이고, 불일치 사유 문장 전체가 보인다(`shots-720/13_inspect_fail.png`). **치명적인 잘림이 아니라 작은 글씨 한계**이며 다시 설계하지 않는다. 1080p에서는 같은 행 글자가 1.5배 크다(정확한 px는 재지 않음).
- **붓기(길게 누르기):** 도구에 누름 지속 시간 옵션이 없어 실제 입력으로는 **검증하지 못했다.** 코드는 Unity 표준 `IPointerDownHandler`/`IPointerUpHandler`와 `Keyboard.spaceKey.isPressed`를 쓴다. PlayMode 테스트와 영상은 게임 내부 플래그로만 확인했다.

## 5. 남은 실제 입력 확인 절차(다음 슬롯에서)

1. 시작 조건: 다른 사람·프로그램이 키보드·마우스를 쓰지 않는다는 확인, G HUB 매크로나 가상 키보드 동작 여부 확인(사용자가 판단), 플레이어 1개, 격리된 `-pps-data-dir`.
2. 창 지정: `list-windows --app pid:<PID>`로 HWND를 확인하고, `--restore-window`는 이 창에 한 번만 쓴다.
3. 매 동작 전후에 스크린샷을 비교한다. 동작 1회에 화면 변화도 1회여야 한다. 그 이상 바뀌면 바로 중단하고 플레이어를 닫는다.
4. 마우스 경로 순서: 시작 → 임무 1 시작 → 요청 6항목 클릭 → 확인 완료 → 새벽차방 선택·주문(반려 사유 확인) → 초록잎상회 주문 → 입고·반품 클릭 → 80℃·찻잔 클릭 → 붓기 → 검수 요청 → 불일치 제외 → 다시 제조 → 다시 검수 → 납품 → 다시 하기.
5. 붓기 길게 누르기는 누름 시간을 조절할 수 있는 앱 지정 도구가 생길 때까지 실제 입력으로는 미검증으로 둔다. 전역 입력 API로 우회하지 않는다.
6. 키보드: 같은 순서를 `press-key`로 확인한다(`Return`, 숫자, `A`/`R`, `T`/`V`, `I`/`X`/`B`). Space 길게 누르기는 5번과 같은 이유로 제외한다.
